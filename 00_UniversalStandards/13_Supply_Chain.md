# Supply Chain

*Know what goes into every artifact, prove where it came from, and refuse anything that cannot
show both.*

The enforceable subset is in `AGENTS.md` → **Supply Chain Rules**; the security policy is `SEC-013`
in `00_UniversalStandards/07_Security_In_Depth.md`. File-level supply-chain anti-patterns are the
`AP-SC-*` rules in `schemas/antipatterns.v1.json`.

---

## 1️⃣ Pin Everything

| Input | Pinned by | Anti-pattern |
| :--- | :--- | :--- |
| Language packages | Exact versions in a committed lockfile (`package-lock.json`, `go.sum`, hashed `requirements.txt`) | `AP-SC-002`, `AP-SC-003` |
| Container base images | Tag and `@sha256:` digest | `AP-SC-004`, `AP-DOCKER-001` |
| Downloaded binaries | Version and published checksum or signature, verified before use | `AP-SC-005`, `AP-SC-001` |
| CI actions and shared workflows | Full commit SHA | `AP-GHA-002` |

Pins are updated deliberately, by an automated update pull request that runs every gate, never by
a floating range resolving to something new at build time.

## 2️⃣ Know What Is Inside: SBOMs

- Every image and release artifact the pipeline builds gets a **software bill of materials** (SPDX
  or CycloneDX), generated by the pipeline (for example with Syft) from the built artifact, not from
  the source tree alone.
- The SBOM is stored with the artifact and attached to it as an attestation, so a vulnerability
  announced later is answered by a query ("which deployed images contain this package?"), not a
  rebuild.

## 3️⃣ Prove Where It Came From: Signing and Provenance

- **Signed by the pipeline's identity.** Images are signed keylessly (for example cosign with the
  CI job's OIDC identity), so no signing key exists to leak; this is the platform's short-lived
  federated identity rule applied to artifacts.
- **Provenance** (SLSA build provenance) records the repository, commit, workflow, and builder.
- **Verified at deploy.** The cluster or deploy step admits only images whose signature and
  provenance name the organization's pipeline and an approved repository. An unsigned image, or one
  built anywhere else, is rejected.
- **Enforced by the platform, not only the pipeline.** Cloud Run's Binary Authorization verifies
  attestations signed with a key, not keyless signatures. So the deployment guard verifies the
  keyless signature, the provenance, and a single-use release token, then attests the digest with
  a Cloud KMS key only its identity can use; Binary Authorization runs only attested digests, which
  also refuses a direct `gcloud run deploy` (`docs/PROGRAM_INCREMENTS.md` §7).

## 4️⃣ Licenses

- A license policy lists allowed, review-required, and denied licenses. The pipeline scans
  dependencies (from the SBOM) against it; a denied license blocks like a CRITICAL finding, a
  review-required one escalates to a person.
- The policy and its exceptions live in a reviewed file with an owner and an expiry, like every
  other exception: `schemas/license_policy.v1.json`. Every consumer evaluates SPDX expressions the
  same way (an OR takes the best term, an AND the worst) and reproduces
  `schemas/examples/license/license_vectors.json`.

## 5️⃣ Vulnerabilities

Dependency and image vulnerabilities follow the gate thresholds in
`00_UniversalStandards/07_Security_In_Depth.md`: CRITICAL or CISA KEV blocks, everything below is
counted on a dashboard. The SBOM makes the same answer available for artifacts already deployed.

A component built from source (for example a minimal build of a library the distribution ships
with dozens of unneeded dependencies) removes findings, but scanners can no longer see it. Pin its
source by checksum, and fail CI when its upstream security channel ships a newer version: the
distribution's security release is the usual signal. Example: coqui-tts builds ffmpeg with only
WAV, MP3, and LAME, which removed 535 of the image's 749 findings, libxml2's CVE-2026-6653 among
them, and
`ffmpeg-current.yml` fails, on every pull request and daily, when Debian's security release moves
past the version the image matches.

---

## Principle

An artifact is trusted only when its inputs are pinned, its contents are listed, and its origin is
signed by the pipeline and verified at deploy.
