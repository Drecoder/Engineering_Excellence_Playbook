# Baseline: Hand-Driven Delivery, 2026-10-21 to 2026-10-26

*The numbers the agent loop has to beat, measured before the Builder and the Reviewer take real
work.*

This is the "before" in the Measure step of `00_UniversalStandards/10_Autonomy_by_Evidence.md`. In
this window, people and coding assistants did the work by hand: a person, Claude Code, and GitHub
Copilot opened, fixed, reviewed, and merged pull requests. The agent loop did none of it. The same
measures, taken from the loop's own telemetry once it runs, are the "after".

## 2️⃣ What Drives the Numbers

- **Change failure rate.** Three causes account for the failed applies: an alert filter the
  Cloud Monitoring API rejected (INC-003), an internal load balancer the API rejected for three days
  (INC-006), and, after that fix, a service account the apply identity is correctly not allowed to
  create (`inference-gpu-bench`, see INC-006). In every case `plan` passed and only the real API
  refused the change: plan is not proof.
- **Lead time.** The p90 is long because several pull requests waited on decisions (exception
  versus egress proxy, repository settings, stacked-PR recovery), not on review.

## 3️⃣ Limits of This Baseline

- **Authorship cannot separate people from agents.** Every pull request lists the owner's account,
  because the person, Claude Code, and Copilot all pushed as the owner. Only Dependabot and the
  playbook-sync workflow appear under their own names. When the loop runs, the Builder and the
  Reviewer must act under their own identities (`AGENTS.md` → Agent Rules), which also makes the
  comparison possible.
- **No token or cost figures.** The hand-driven work was not instrumented. The loop records
  `gen_ai.usage.*` on every model call (`02_BackendZone/04_Telemetry_Standards.md`), so cost per
  merged change becomes a measure from its first run.
- **Small sample, one window.** Six days and 13 applies is enough to show the starting point,
  not to set control limits. Control charts start once the loop produces a steady flow
  (`10_Autonomy_by_Evidence.md` §6).

## 4️⃣ The Comparison to Make

Once the loop takes real work, report the same three measures (lead time, change failure rate,
merged changes per repository), plus review rounds per change (`review_loop_rounds`, p90 ≤ 3) and
tokens and cost per merged change, from the loop's telemetry. The goal is lower lead time and a
lower change failure rate at a known cost, without moving any protected class past L2.

## Principle

Measure the hand-driven process before replacing it, so the loop's numbers mean something.
